二、流程設計說明（回答作業步驟三）

1. 資訊如何取得、整理、檢查與生成？

  1. 取得資料（Discuss + Raw）：先寫定 discussion/00-discuss-before-generate.md，再收集 6 篇真實一手來源存入唯讀 raw/。
  2. 整理編譯（Ingest Loop）：依 SCHEMA.md 逐篇抽取概念，建立或更新 16 篇 wiki/*.md，同步 index.md 與 log.md。
  3. 知識健檢（Gate 1: WikiLint）：自動化腳本驗證 Frontmatter、83 條 [[wikilink]] 零斷鏈、零孤島、索引同步與來源一致。
  4. 大綱前移檢查（Gate 2: OutlineGate）：先鎖定投影片頁數、先修順序 DAG、單頁字數上限與覆蓋率，才允許寫投影片正文。
  5. 逐頁溯源與實機檢查（Gate 3 & 4）：每頁獨立比對 Citation Drift、術語先後順序、初學者字數負荷，並用 Playwright 以 1280×720 實機走訪確認零裁切、零 JS 錯。

2. 重複步驟、重做節點與設計理由

  • 哪些步驟會重複執行？
    • Ingest 迴圈：針對 SRC-01～SRC-06 反覆執行「讀檔 → 寫 Wiki → 更新索引與日誌 → 執行 WikiLint」。
    • 單頁生成與修正迴圈：任一投影片若在 SlideGate 或 BrowserGate 失敗，僅重寫該頁草稿再重驗，避免污染乾淨頁。
  • 為什麼要這樣設計？

    這正是本專案主題 Context Engineering 的親身實踐：用 index.md 做 Select、把規格與草稿存為檔案做 Write、將四個檢查拆成獨立腳本節點做 Isolate，從根本避免把全部原始文章塞進同一個長 Prompt 造成的 Context Rot 與幻覺漂移。

四、深度反思（回答作業步驟四）

1. 哪一個節點最常出錯？
「草稿生成節點（DraftSlides）」最常出錯，在 Run #1 (v1) 實測中一次出現了三類典型錯誤：
  • 初學者資訊過載與舞台溢出：第 3 頁塞入過多長段落卡片（超過字數預算），在 1280×720 實機檢測下導致舞台垂直溢出。
  • 先修術語順序倒置（Jargon Before Intro）：第 2 頁尚未解釋 KV-Cache 與 Compaction 的意思就直接丟出英文術語，破壞零基礎體驗。
  • 來源引用漂移（Citation Drift）：第 5 頁只綁定了介紹失效模式的 Wiki 頁（SRC-02、SRC-05），卻在簡報出處誤植未出現在該 Wiki 的 [SRC-04]。
2. 發現問題後，把檢查往前移到了哪一個步驟？為什麼因此修改 Workflow / Graph？
在 v1 初版線性管線中，檢查全擠在最後生成完才做，每次發現「順序講反」或「單頁太擠」就得重寫好多頁（返工成本極高）。
因此我們在 v2 流程圖中將 Workflow 改為帶有前置攔截關卡（Shift-Left Gate）與局部重試迴圈的狀態圖：
  1. 把「來源完整性與 Wikilink 健康度」提前到 Gate 1: WikiLintGate，確保知識庫本身不帶毒（Prevent Context Poisoning）。
  2. 把「先修順序 DAG、單頁字數上限（<= 450 字）與覆蓋率檢查」大幅前移到寫內文之前的 Gate 2: OutlineGate，讓 AI 寫正文前就被鎖死教學順序與版面預算。
  3. 在 Gate 3: SlideGate 加入逐頁溯源與術語順序檢查，並在最後補上 Gate 4: BrowserGate 實機瀏覽器檢驗。結果在 Run #2 (v2) 中，全部 4 道關卡與 14 頁 1280×720 渲染皆達到 0 錯誤通過。
所有審計數據皆由 pipeline/run_pipeline.py 真實生成，原始 JSON 與 Markdown 報告位於 repo logs/ 目錄。
